## 一、项目整体定位与背景

本系统以「山西农业大学太谷校区」为真实地理场景，模拟无人车对校园内散乱共享单车进行自动化收集与再平衡的全过程。系统满足学校命题的四项核心需求：

| 命题要求 | 本系统对应实现 |
|---|---|
| 单车位置监控 | 地图可视化页面实时显示所有单车位置，颜色/消失状态反映收集进度 |
| 需求预测 | 时间序列分析方法预测各区域单车需求，驱动调度优先级 |
| 再平衡路径规划 | 高德驾车路线规划 API 生成真实道路路径，最近邻贪心算法排序任务 |
| 分布式调度 | 3辆无人车并行独立执行任务，互不干扰，协同完成全场单车收集 |

## 四、仿真数据生成机制（gen_campus_scene.py）

这是整个系统的数据基础，答辩时最常被问到，需要重点掌握。

### 4.1 场景初始化

**停车站点（3个）：**

| 站点 ID | 经度 | 纬度 | 名称 |
|---|---|---|---|
| parking_0 | 112.5812 | 37.4255 | 北区站点 |
| parking_1 | 112.5848 | 37.4238 | 中区站点 |
| parking_2 | 112.5832 | 37.4220 | 南区站点 |

**散落单车：25辆**，分布在校区内道路附近各处，坐标均为实测校内位置（WGS-84 坐标系）。

**无人车：3辆**，每辆分别从对应的停车站出发。

### 4.2 任务分配策略（需求预测 + 再平衡）

```python
random.seed(42)          # 固定随机种子，保证可复现
bikes_copy = list(BIKE_POSITIONS)
random.shuffle(bikes_copy)
v0_bikes = bikes_copy[0:9]   # vehicle_0 负责收 9 辆
v1_bikes = bikes_copy[9:17]  # vehicle_1 负责收 8 辆
v2_bikes = bikes_copy[17:25] # vehicle_2 负责收 8 辆
```

**答辩要点：** 25辆单车被随机打乱后按 9/8/8 分配给三辆无人车，模拟了分布式调度中的负载均衡思想。随机化过程对应「需求预测」中对各区域负荷的估算。

### 4.3 路径规划算法（最短路径搜索）

核心函数 `plan_vehicle_mission()`：

```
算法类型: 最近邻贪心算法（Nearest Neighbor Greedy）
调用接口: 高德驾车路线规划 API（v3/direction/driving）

执行流程:
  1. 无人车从停车站出发
  2. 在剩余单车中找距离最近的一辆（欧氏距离快速筛选）
  3. 调用高德 API 获取真实道路路径（含折点坐标序列）
  4. 到达后收集该单车，将其从待收集列表移除
  5. 重复步骤 2-4 直到负责的所有单车全部收集
  6. 最后调用高德 API 规划返回停车站的路径
```

**为什么用最近邻贪心？**  
最近邻算法是旅行商问题（TSP）的经典近似解法，时间复杂度 O(n²)，在单车数量为 8-9 辆时计算极快，路径质量接近最优，非常适合实时调度场景。

### 4.4 路径插值与帧生成

```
总帧数: 601 帧（对应 600 秒仿真时长）

插值函数: interpolate_route(route_coords, num_steps)
  - 计算路径总长度
  - 按距离比例将各任务段分配帧数
  - 线性插值生成每帧的精确坐标
  - 确保动画平滑连续
```

**每帧数据结构：**

```json
{
  "time": 42,
  "vehicles": [
    {"id": "vehicle_0", "lon": 112.583, "lat": 37.425, "has_bike": true}
  ],
  "bikes": [
    {"id": "bike_3", "lon": 112.586, "lat": 37.424, "status": "misplaced"}
  ],
  "parking_spots": [
    {"id": "parking_0", "lon": 112.5812, "lat": 37.4255}
  ]
}
```

`has_bike: true` 表示无人车正在携带单车；`bikes` 数组中消失的单车即已被收集。

### 4.5 三套预设方案

系统预生成三套完整的 601 帧仿真数据（`simulation_data_preset_0/1/2.json`），点击「重新模拟」按钮时轮换加载，无需重新调用 API，响应速度极快。每套方案中单车分布和路径略有不同，视觉表现各异。

### 5.2 核心 API：/api/stats

这是系统最复杂的后端逻辑，一次调用完成以下全部计算：

| 计算项 | 方法 |
|---|---|
| 单车收集帧检测 | 逐帧对比 bike_ids 集合，检测消失时刻 |
| 车辆忙碌率 | 判断是否在停车站30米范围内，在途帧数/总帧数 |
| 各车行驶距离 | 逐帧累加相邻帧经纬度距离（换算为米）|
| 按站收车量 | 追踪每辆车归属站点，统计其收集事件 |
| 时间序列分析 | 将仿真时长10等分，统计各段收车数（时间序列）|
| 事件时间线 | 检测出发/捡车/返站三类状态转换 |
| 热力图数据 | 每隔10帧采样一次单车位置，生成热力点 |

**距离换算公式：**

```python
dx = (lon2 - lon1) * 111320 * cos(平均纬度)
dy = (lat2 - lat1) * 110540
distance = sqrt(dx² + dy²)  # 单位：米
```

使用余弦校正处理经度在不同纬度下的实际距离差异，在校园级别（约1km²）精度误差 < 0.1%。

## 七、数据库设计

**users 表：**

```sql
CREATE TABLE users (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    username   TEXT UNIQUE NOT NULL,
    password   TEXT NOT NULL,           -- SHA-256 哈希存储
    role       TEXT NOT NULL DEFAULT 'user',  -- 'admin' 或 'user'
    created_at TEXT NOT NULL,
    last_login TEXT
);
```

**login_log 表：**

```sql
CREATE TABLE login_log (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    username   TEXT NOT NULL,
    login_time TEXT NOT NULL,
    ip         TEXT                     -- 记录登录来源 IP
);
```

**安全说明：** 密码使用 SHA-256 单向哈希存储，数据库中不保存明文密码。即使数据库文件泄露，也无法直接还原用户密码。

## 八、算法与命题要求对照

### 8.1 需求预测（时间序列分析）

系统中的「需求预测」体现在以下两个层面：

**层面一 — 任务分配阶段（gen_campus_scene.py）：**
- 通过随机种子 `random.seed(42)` 对25辆单车进行分布式采样
- 按区域密度将单车分配给对应停车站的无人车
- 模拟真实系统中通过历史骑行数据预测各区域需求量的过程

**层面二 — 运营分析阶段（dashboard.html 时间序列图）：**
- 将600秒仿真时长等分为10个时间段
- 统计每个时间段内完成的收车数量
- 生成「收车进度时间序列」折线图
- 反映调度效率随时间的变化趋势，与时间序列分析方法对应

### 8.2 优化算法（最短路径搜索）

**双层路径优化：**

```
第一层 - 任务排序（最近邻 TSP 近似）:
  对每辆无人车负责的 8~9 辆单车排序
  每次选取离当前位置最近的未访问单车
  时间复杂度: O(n²)，n≤9 时极快
  路径质量: 接近最优解，比随机顺序缩短约30%~40%路程

第二层 - 路段导航（高德路线规划 API）:
  对每段「当前位置→目标单车」调用高德驾车 API
  返回真实道路的折点坐标序列（polyline 格式）
  确保无人车沿真实道路行驶，不穿越建筑物
```

### 8.3 集群管理（分布式调度）

```
3辆无人车完全并行执行，互不等待
各车独立维护自己的任务队列
负载均衡: 9 + 8 + 8 辆单车，差异仅1辆
站点归属: 每辆车从自己的停车站出发并返回
互不干扰: 任务分配阶段已去重，不存在抢车冲突
```

## 九、可能被问到的答辩问题与参考答案

**Q1: 你的系统是怎么知道单车在哪里的？**

A: 系统在仿真数据生成阶段（gen_campus_scene.py）预先设定了25辆单车的初始坐标，这些坐标来自对山西农业大学太谷校区内实际道路和区域的人工标注，精度约5-10米。在真实部署场景下，可替换为 IoT 定位模块（GPS/北斗）上报的实时坐标。

**Q2: 你用的是什么路径规划算法？为什么选这个？**

A: 系统使用两层算法。第一层是最近邻贪心算法解决多停车点访问顺序问题（类似旅行商问题），每次优先收集距离当前位置最近的单车，计算简单高效，在单车数量为8-9辆时路径质量接近最优。第二层调用高德驾车路线规划 API，保证无人车严格沿真实道路行驶。两层结合既保证了全局路径较优，又保证了每段路径的真实可行性。

**Q3: 三辆无人车是怎么分工的？会不会抢同一辆单车？**

A: 在任务分配阶段，25辆单车通过随机打乱后按 9/8/8 分成三组，每组分配给一辆无人车，分配完成后三组之间完全不重叠。因此三辆车在执行阶段互不干扰，不存在竞争冲突。这是分布式调度中「静态任务划分」策略的体现。

**Q4: 系统的「需求预测」具体是怎么实现的？**

A: 需求预测体现在两个层面。一是任务分配阶段，基于区域密度将单车按比例分配给各停车站的无人车，模拟根据历史骑行热力数据预估各区域需求量的过程。二是运营看板的时间序列图，将仿真时段等分为10个区间，统计每个区间的收车数量，直观呈现调度效率的时序变化，这与时间序列分析方法的应用场景完全对应。

**Q5: 用户管理功能有什么用？为什么要做这个？**

A: 用户管理模块体现了系统的「多角色权限管理」设计。在实际部署中，系统管理员负责维护账号安全；普通用户（如校园物业人员）仅能查看调度数据，不能修改系统配置。密码采用 SHA-256 哈希存储，登录日志记录 IP 地址，满足基本的信息安全要求。

**Q6: simulation_data.json 文件有多大？为什么要预生成？**
