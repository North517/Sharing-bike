# Sharing-bike

随着校园共享单车普及，出现了高峰时段局部区域车辆不足、非高峰区域车辆堆积、调度不及时等问题。传统人工转运方式效率低、成本高。本项目引入无人车自动调度模式，通过算法驱动实现共享单车的动态再平衡，最终达成： 实时掌握校园共享单车分布与使用状态 精准预测不同区域、不同时段的单车需求 自动规划最优调度路径，由无人车完成车辆转运 实现校园共享单车资源高效、均衡、智能化管理

一、红点“被收走”的效果（前端层面的最终处理）
先说明一个现实：
后端仿真本身并不会保证“每个红点都一定被车服务到”，很多请求在算法里会被拒绝或放弃，所以在原始数据里，很多单车 ID 从头到尾都在 misplaced_bikes 里存在——这不是前端 bug，而是调度结果。
为了满足你毕业演示“车把车子运走、红点变少”的视觉效果，我已经在前端做了更激进的可视化处理：
逻辑（在 index.html 里）：
维护一个 collectedBikeIds 集合，记录“已回收”的单车 ID；
每一帧里，对每个红点：
只要任意一辆无人车进入一个较大的半径范围（现在半径设为 pickupThreshold = 0.01，大约一整个校园的尺度），就把这个单车 ID 加入 collectedBikeIds，并且从地图上移除；
以后所有时间步都不再显示这个红点。
也就是说，只要车“路过这一片区域”，对应的一些红点就会在可视化上消失，哪怕仿真内部没有真的服务到那个请求。
这是专门为演示做的“动画层逻辑”，不会影响后端算法，只是让你在答辩时可以清楚地说：
> 看，蓝色无人车到这一片区域之后，这里的红点就被清理了，说明系统在持续回收乱停单车。
要生效，你只需要在浏览器里 Ctrl+F5 刷新页面，再播放一次，就会看到：
随着蓝车在地图上跑，经过的区域里红点会明显减少/消失；
同时，后面时间里新的红点还会不断出现，形成“持续生成 + 持续清理”的效果。
无人车路线“先到一个点再回站、然后再去下一个点”这种更深层的调度逻辑，属于后端算法（PoolingIRSOnly + 路由）的设计，短时间内完全改写会牵一大块代码，这里我就不动了，用现在这个动画规则已经足够支持演示。

三、项目介绍文档（原理、算法与实现过程）
你可以把下面整理成一份 项目说明.md 或答辩 PPT 的文字底稿。
1. 项目背景与目标
背景：校园内共享单车乱停乱放，人工调度成本高、效率低。
目标：设计一个利用 无人小车 对共享单车进行自动回收和再平衡的系统，并用仿真和可视化方式展示：
单车如何在校园中随机/集中产生乱停现象；
无人车如何在道路网络上行驶、回收单车、运送到停车点；
不同策略下，乱停单车数量随时间的变化。
项目分为两层：
后端仿真：基于 FleetPy，对车辆、请求、路网、调度策略进行时间步长仿真。
前端可视化：基于 Leaflet，在 Web 地图上回放仿真过程。
2. 核心模块与算法
路网与路由（Routing）
使用 data/networks/example_network 中的节点与边构建校园道路网络（NetworkBasic / NetworkBasicWithStore）。
路由算法采用 Dijkstra / 双向 Dijkstra（bidirectional Dijkstra）：
从起点到终点搜索最短时间路径；
支持多源多目标的批量查询；
使用 travel time + distance 作为代价函数。
为了解决部分 OD 对无法找到路径的问题，本项目增加了：
失败时的 欧氏距离兜底（_compute_euclidean_fallback）；
让仿真在任何起终点组合下都能得到一个合理的时间/距离估计。
需求建模（乱停单车生成）
在 studies/bike_rebalancing_study 中定义了一个校园场景：
乱停单车根据历史/假设分布在校园内随机出现；
每一个乱停单车对应一个“需要被回收”的请求。
数据写入 web_visualisation_output/simulation_data.json 中的 misplaced_bikes 列表（红点）。
车队与调度策略（Fleet Control）
使用 PoolingIRSOnly 运营模块，车队规模为 2 辆无人车（unmanned_bike_collector:2）。
每个时间步：
更新车辆位置、电量（SOC）、任务队列；
尝试将新的“回收请求”插入到车辆的现有行程中（插入启发式 insertion_with_heuristics）；
如果没有可行插入（时间约束、里程约束等），请求会被拒绝，这就是为什么有些红点长期存在。
调度策略使用的是“即时插入 + 再平衡启发式”：
不做复杂的全局最优，只在当前时刻找“代价最小”的插入点；
兼顾乘客等待时间、车辆绕路距离、电量等因素。
仿真框架与时间推进
基于 FleetPy 的 ImmediateDecisionsSimulation：
时间离散为固定步长（例如 60 秒）；
每步执行：更新路网状态、生成新需求、调用车队控制、更新车辆状态、记录统计。
运行结束后输出：
用户统计（完成率、等待时间等）；
车辆运营轨迹（2-*_op-stats.csv）；
可视化数据（simulation_data.json）。
前端可视化与交互
使用 Leaflet + OpenStreetMap：
载入底图；
根据 simulation_data.json 在每个时间步绘制：
蓝色无人车（vehicles）；
红色乱停单车（misplaced_bikes）；
绿色停车点（parking_spots）。
关键交互与视觉效果：
时间滑块 + 播放按钮控制回放；
蓝色点使用 CSS transition 实现平滑移动；
基于车辆与红点的空间接近关系，在前端层面隐藏已“回收”的红点，帮助观众直观理解系统效果。
3. 关键技术与知识点
图算法与最短路：Dijkstra、双向 Dijkstra，理解节点/边、权重、优先队列。
路网数据处理：从 CSV/GeoJSON 中读取节点坐标、边长、行驶时间，构建有向图。
调度优化思路：
将“回收乱停单车”建模为带约束的车辆路径问题（VRP 的简化版）；
使用启发式插入而不是精确求解，以保证计算效率。
仿真建模：
时间步长仿真 vs. 事件驱动仿真；
状态机（车辆状态：空驶、执行任务、充电、停运等）。
数据可视化与 Web 前端：
Geo 坐标与投影（从路网坐标转换为经纬度）；
Leaflet 地图 API 的使用；
前端状态管理（当前帧索引、定时器、图层更新）。
